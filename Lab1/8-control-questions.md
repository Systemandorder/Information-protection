# 8. Контрольні питання

Короткі відповіді з посиланнями на відповідні файли, детальні команди й пояснення дивись там.

## Загальне

**Які підсистеми захисту є в Лінуксі і в чому їхня робота.** Автентифікація, це перевірка, хто ти. Авторизація, тобто права доступу, це перевірка, що тобі дозволено. Аудит і журнали фіксують, що відбувалось. Мережний захист контролює, хто може достукатись до системи ззовні. Налаштовуються вони відповідно через PAM, права файлів і ACL, auditd чи rsyslog, iptables чи nftables.

**Ідентифікатори поточного користувача.** Команди `id` і `whoami`, дивись [1-accounts.md](1-accounts.md).

**Де зберігається інформація про облікові записи.** `/etc/passwd` для списку користувачів, `/etc/shadow` для хешів, доступний лише root, `/etc/group` для груп. Дивись [1-accounts.md](1-accounts.md).

**Хто суперкористувач.** root, UID 0. Будь-який обліковий запис з UID 0 фактично стає суперкористувачем, не обов'язково саме з іменем root, бо ядро перевіряє UID, а не ім'я. Особливі повноваження root це обхід майже всіх перевірок прав доступу, керування будь-якими процесами, монтування файлових систем, зміна мережних налаштувань і так далі.

## Паролі

**Стійкість пароля root через John the Ripper.** Дивись [1-accounts.md](1-accounts.md), пункт 2.1.12. Якщо пряме парольне входження root вимкнене, типово в Kali, для коректного тесту тимчасово задай тестовий пароль через `sudo passwd root`, прожени John, потім постав назад `sudo passwd -l root`.

**Облікові записи без пароля.** Дивись [1-accounts.md](1-accounts.md), пункт 2.1.9.

## Права доступу

**Права доступу для файлу.** Команда `ls -l <FILE>`, дивись README, розділ про права за 5 хвилин.

**Скільки категорій користувачів можуть мати різні права на файл.** Три. Власник, group, u і g, та решта, o.

**Зміна прав за замовчуванням для нових файлів.** Команда `umask`, дивись [3-permissions.md](3-permissions.md), пункт 4.1. Значення umask 022 дає новим файлам права rw-r--r--.

**Що означає "x" для файлу.** Право запустити файл як програму чи скрипт.

**Що означають "r" і "x" для каталогу.** r дає можливість бачити список імен усередині. x дає можливість заходити в каталог і звертатись до файлів усередині за іменем, навіть не бачачи списку, якщо немає r, це темний каталог, дивись [3-permissions.md](3-permissions.md), пункт 4.5.

**Які права потрібні, щоб видалити файл чи каталог.** Право запису і проходу, w і x, у батьківському каталозі. Права самого файлу на видалення не впливають, якщо немає sticky bit на батьківському каталозі.

**Дія SUID, SGID і sticky.** Дивись [3-permissions.md](3-permissions.md), пункти 4.3 і 4.5.

**Атрибути immutable і append.** Пошук дивись [2-files-search.md](2-files-search.md), пункт 3.1.5. Демонстрація дії в [3-permissions.md](3-permissions.md).

**Права власника файлу.** Право читати, писати й виконувати незалежно від групи й інших. Тільки власник і root можуть змінювати права через `chmod`.

**Зміна власника чи групи.** Команда `chown <USER>:<GROUP> <FILE>`, дивись [1-accounts.md](1-accounts.md) і [3-permissions.md](3-permissions.md), пункт 4.3.

**Чи можна приховати файл від root.** Ні, стандартними правами не можна, root обходить перевірки прав. Хіба що шифруванням вмісту, тоді root бачить файл, але не розшифрований вміст.

## Посилання

**Жорстке проти символічного посилання.** Дивись [2-files-search.md](2-files-search.md), терміни й пункт 3.3, та [3-permissions.md](3-permissions.md), пункт 4.2.

**Жорстке посилання на жорстке чи символічне посилання.** "Жорстке на жорстке" не має окремого сенсу, обидва імені однаково вказують на той самий inode. Жорстке посилання на символічне на практиці слідує за symlink і лінкує те, на що він вказує, а не сам файл-ярлик. Символічне на символічне можливе, виходить ланцюжок посилань.

**Скільки посилань може мати файл чи каталог.** Жорстких посилань обмежена кількість, задається лічильником посилань, st_nlink. Символічних посилань необмежено, бо це окремі файли, які просто містять шлях.

## Запуск програм

**Яка з кількох однойменних копій програми реально запускається 🟢**

```bash
which id
# which показує першу знайдену копію в $PATH, саме вона й запуститься

type -a id
# type -a показує всі знайдені копії за порядком каталогів $PATH

echo $PATH
# показує сам порядок каталогів пошуку

hash id
# hash в bash, або hash без -t у zsh, показує, який шлях шелл уже закешував
# для цієї команди в поточній сесії
# може відрізнятись від "which", якщо файл замінили після першого запуску
```

Безпековий аспект. Якщо атакуючий здатен дописати свій каталог на початок `$PATH`, або підсунути однойменний файл у каталог, що стоїть раніше в `$PATH`, він підмінить програму, яку реально запустить жертва. Це називається PATH hijacking. Тому root і скрипти з sudo мають використовувати абсолютні шляхи, а не покладатись на `$PATH`.

## ACL

**ACL для нормативного керування доступом.** Задати default ACL на кореневому каталозі проєкту так, щоб нові файли завжди успадковували потрібні групові права незалежно від umask користувача, що їх створив, дивись `setfacl -d` у [4-sudo-acl.md](4-sudo-acl.md).
