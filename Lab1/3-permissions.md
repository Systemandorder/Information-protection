# 3. Права доступу: umask, посилання, SUID/SGID, темний каталог

Заготовки (`<USER>`, `<FILE>` тощо) і позначки 🟢🟡🔴 — дивитися README.

## Терміни

**umask** — маска, яка віднімається від максимальних прав при створенні нового файлу/каталогу.
**SUID (Set User ID)** — біт, через який програма виконується з правами ВЛАСНИКА файлу, а не того, хто її запустив.
**SGID (Set Group ID)** — те саме, але з правами ГРУПИ файлу; для каталогу нові файли в ньому успадковують групу каталогу.
**sticky bit** — на каталозі дозволяє видаляти файли лише їхньому власнику, навіть якщо каталог доступний на запис усім.
**«темний» каталог** — каталог, у який можна писати (є `x`+`w`), але не можна переглянути список файлів (немає `r`).
**ефективний UID/GID (euid/egid)** — права, з якими процес РЕАЛЬНО виконується зараз; можуть відрізнятись від реального uid завдяки SUID.

## 4.1 Де задається umask 🟢

```
umask
# umask            — показати поточну маску (зазвичай 022 або 002)

grep -i -E 'umask|USERGROUPS_ENAB' /etc/login.defs /etc/profile ~/.bashrc 2>/dev/null
# grep -i -E        — пошук за розширеним регулярним виразом, без урахування регістру
# umask|USERGROUPS_ENAB   — два слова, за якими шукаємо
# /etc/login.defs   — тут прописане системне значення UMASK
# USERGROUPS_ENAB yes — якщо увімкнено і в користувача є особиста група (ім'я = його логін),
#                       система застосовує м'якший umask 002 замість 022
```

Підсумкове право нового файлу = 666 (rw-rw-rw-) мінус umask, нового каталогу = 777 мінус umask.

## 4.2 Жорстке і символічне посилання + chmod 🟡

```
mkdir <DIR>
touch <FILE>
# touch     — створити порожній тестовий файл (нульового розміру)

ln <FILE> <DIR>/hard.txt
# ln (без -s)   — жорстке посилання (hard link): друге ІМ'Я того самого inode,
#                 а не копія файлу

ln -s ../<FILE> <DIR>/sym.txt
# ln -s         — символічне посилання (symlink): окремий маленький файл-ярлик,
#                 що зберігає лише ТЕКСТ шляху до цілі (../<FILE> — відносний шлях)

ls -l <DIR>/
# ls -l   — показати права, кількість жорстких посилань, власника, розмір, дату

chmod 777 <FILE>
# chmod 777 <FILE>   — змінюємо права самого файлу (rwxrwxrwx)

ls -l <DIR>/
```

Жорстке посилання одразу покаже ті самі нові права — **права живуть в inode**, спільному для всіх жорстких посилань на один файл. Символічне посилання завжди показує `lrwxrwxrwx` і не змінюється його права фактично ігноруються системою, реально перевіряються права цілі, на яку воно вказує.

```
mkdir other_dir
mv <DIR>/hard.txt <DIR>/sym.txt other_dir/
# mv   — перенести обидва посилання в інший каталог
#        (символічне зберігає ВІДНОСНИЙ шлях, тому після переносу ще може влучити в ціль,
#        якщо структура каталогів це дозволяє)

rm <FILE>
# rm <FILE>   — видалити ОРИГІНАЛЬНИЙ файл (те ім'я, з якого все починалось)

cat other_dir/hard.txt
# працює — inode і дані ще живі, доки лишається хоч ОДНЕ ім'я (жорстке посилання) на нього

cat other_dir/sym.txt
# "No such file or directory" — символічне посилання зберігало лише ТЕКСТ старого шляху,
# а не сам inode, тому воно "битe" після видалення оригіналу
```

Прибрати: `rm -r <DIR> other_dir`.

## 4.3 SUID на скрипті й на бінарнику 🔴

```
nano <SCRIPT>
# nano <SCRIPT>   — створити/відкрити текстовий файл скрипта, наприклад:
# #!/bin/bash
# echo "run as:"; id

chmod +x <SCRIPT>
# chmod +x   — додати право на ВИКОНАННЯ (без нього shell відмовить запускати файл)

./<SCRIPT>
# запуск звичайним користувачем — euid (ефективний UID) = твій власний UID, як і очікувано
```

```
sudo chown root:root <SCRIPT>
# chown root:root   — зробити ВЛАСНИКОМ файлу root (інакше SUID не матиме сенсу демонструвати)

sudo chmod u+s <SCRIPT>
# chmod u+s   — встановити біт SUID, замість "x" власника з'явиться "s"

ls -l <SCRIPT>
# очікувано: -rwsr-xr-x

./<SCRIPT>
# euid усе одно залишиться твоїм — ЯДРО ЛІНУКСА ІГНОРУЄ SUID для файлів зі строчкою #!
# (інтерпретовані скрипти). Це свідомий захист ядра, інакше будь-хто міг би підмінити
# сам інтерпретатор (/bin/bash) у своєму $PATH і отримати root через чужий SUID-скрипт.
```

Щоб побачити, що SUID РЕАЛЬНО працює, потрібен скомпільований бінарник (не текстовий скрипт):

```
cp /usr/bin/id ~/id_test
# cp /usr/bin/id   — копіюємо ГОТОВУ скомпільовану програму id (не скрипт!)

sudo chown root:root ~/id_test
sudo chmod u+s ~/id_test
# ті самі дії, що й вище, але тепер на бінарнику

~/id_test
# euid=0(root) — ТЕПЕР спрацювало: ядро не блокує SUID для скомпільованих ELF-файлів

sudo chown root:shadow ~/id_test
sudo chmod u-s,g+s ~/id_test
# u-s   — зняти SUID
# g+s   — встановити SGID (права групи файлу, зараз це shadow)

~/id_test
# egid=42(shadow) — тепер діє SGID замість SUID: ефективна ГРУПА стала group файлу
```

Прибрати: `rm ~/id_test <SCRIPT>`.

## 4.5 Темний каталог 🟡

```
mkdir <DIR>
chmod 1733 <DIR>
# chmod 1733:
#   1    — sticky bit (видаляти файли всередині може лише ВЛАСНИК кожного файлу)
#   7    — rwx власнику каталогу
#   3    — -wx групі ("w"+"x", без "r")
#   3    — -wx решті (-wx, без "r")
# тобто "група" і "решта" МОЖУТЬ заходити й створювати файли (є x і w),
# але НЕ можуть побачити список файлів усередині (немає r) — звідси "темний"

ls -ld <DIR>
# -d   — показати інформацію про сам каталог, а не його вміст
# очікувано: drwx-wx-wt
```

Перевірка під іншим користувачем:

```
sudo -u <USER> touch <DIR>/secret.txt
# sudo -u <USER>   — виконати команду від імені іншого користувача (не змінюючи повністю сесію)
# дозволено — є право на запис (w) і прохід (x) у каталог

sudo -u <USER> ls -l <DIR>
# Permission denied — немає права читати список файлів (r)
```

Власник каталогу бачить і читає файл як завжди. Якщо потрібна конфіденційність самого ВМІСТУ файлу (а не тільки його існування)— додатково потрібні жорсткі права на сам файл (наприклад, 600); сам темний каталог ховає лише перелік імен, не вміст конкретного файлу, якщо хтось знає його точну назву.
