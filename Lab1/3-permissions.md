# 3. Права доступу: umask, посилання, SUID/SGID, темний каталог

Заготовки (`<USER>`, `<FILE>` тощо) і позначки 🟢🟡🔴 дивись у README.

## Терміни

**umask** маска, яку система віднімає від максимальних прав при створенні нового файлу чи каталогу.

**SUID (Set User ID)** біт, через який програма виконується з правами ВЛАСНИКА файлу, а не того, хто її запустив.

**SGID (Set Group ID)** те саме, але з правами ГРУПИ файлу. Для каталогу нові файли всередині успадковують його групу.

**sticky bit** на каталозі дозволяє видаляти файли лише їхньому власнику, навіть якщо каталог доступний на запис усім.

**«темний» каталог** каталог, у який можна писати (є `x` і `w`), але не можна переглянути список файлів усередині (немає `r`).

**ефективний UID/GID (euid/egid)** права, з якими процес реально виконується зараз. Можуть відрізнятись від реального UID завдяки SUID.

## 4.1 Де задається umask 🟢

```
umask
# показує поточну маску, зазвичай 022 або 002

grep -i -E 'umask|USERGROUPS_ENAB' /etc/login.defs /etc/profile ~/.bashrc 2>/dev/null
# grep -i -E шукає за шаблоном без урахування регістру
# /etc/login.defs це файл, де прописане системне значення UMASK
# якщо USERGROUPS_ENAB увімкнено і в користувача є особиста група з його іменем,
# система застосовує м'якший umask 002 замість 022
```

Право нового файлу дорівнює 666 мінус umask. Право нового каталогу дорівнює 777 мінус umask.

## 4.2 Жорстке і символічне посилання плюс chmod 🟡

```
mkdir <DIR>
touch <FILE>
# touch створює порожній тестовий файл

ln <FILE> <DIR>/hard.txt
# ln без -s створює жорстке посилання. Це друге ім'я того самого inode, а не копія файлу

ln -s ../<FILE> <DIR>/sym.txt
# ln -s створює символічне посилання. Це окремий маленький файл-ярлик,
# який зберігає лише текст шляху до цілі

ls -l <DIR>/
# показує права, кількість жорстких посилань, власника, розмір і дату

chmod 777 <FILE>
# змінює права самого файлу на rwxrwxrwx

ls -l <DIR>/
```

Жорстке посилання одразу покаже ті самі нові права. Права зберігаються в inode, спільному для всіх жорстких посилань на один файл. Символічне посилання завжди показує `lrwxrwxrwx` і не змінюється. Його власні права фактично ігноруються системою, перевіряються права цілі, на яку воно вказує.

```
mkdir other_dir
mv <DIR>/hard.txt <DIR>/sym.txt other_dir/
# переносить обидва посилання в інший каталог

rm <FILE>
# видаляє оригінальний файл

cat other_dir/hard.txt
# працює, бо дані ще живі, доки лишається хоч одне ім'я (жорстке посилання) на inode

cat other_dir/sym.txt
# видає "No such file or directory", бо символічне посилання зберігало лише текст старого шляху
```

Прибрати: `rm -r <DIR> other_dir`.

## 4.3 SUID на скрипті й на бінарнику 🔴

```
nano <SCRIPT>
# створює або відкриває текстовий файл скрипта, наприклад
# #!/bin/bash
# echo "run as:"; id

chmod +x <SCRIPT>
# додає право на виконання

./<SCRIPT>
# запуск звичайним користувачем. euid дорівнює твоєму власному UID, як і очікувалось
```

```
sudo chown root:root <SCRIPT>
# робить власником файлу root

sudo chmod u+s <SCRIPT>
# встановлює біт SUID, замість "x" власника з'являється "s"

ls -l <SCRIPT>
# очікуваний результат -rwsr-xr-x

./<SCRIPT>
# euid усе одно залишається твоїм. Ядро Лінукса ігнорує SUID для файлів зі строчкою #!
# Це свідомий захист. Інакше будь-хто міг би підмінити інтерпретатор у $PATH
# і отримати root через чужий SUID-скрипт
```

Щоб побачити, що SUID реально працює, потрібен скомпільований бінарник, а не текстовий скрипт.

```
cp /usr/bin/id ~/id_test
# копіює готову скомпільовану програму id

sudo chown root:root ~/id_test
sudo chmod u+s ~/id_test
# ті самі дії, що вище, але тепер на бінарнику

~/id_test
# euid=0(root). Тепер спрацювало, бо ядро не блокує SUID для скомпільованих файлів

sudo chown root:shadow ~/id_test
sudo chmod u-s,g+s ~/id_test
# u-s знімає SUID, g+s встановлює SGID з групою shadow

~/id_test
# egid=42(shadow). Тепер діє SGID замість SUID, ефективна група стала групою файлу
```

Прибрати: `rm ~/id_test <SCRIPT>`.

## 4.5 «Темний» каталог 🟡

```
mkdir <DIR>
chmod 1733 <DIR>
# перша цифра 1 це sticky bit, видаляти файли всередині може лише власник кожного файлу
# друга цифра 7 це rwx власнику каталогу
# третя цифра 3 це -wx групі, без r
# четверта цифра 3 це -wx решті, без r
# група і решта можуть заходити й створювати файли, бо є x і w,
# але не бачать список файлів усередині, бо немає r. Звідси "темний"

ls -ld <DIR>
# -d показує інформацію про сам каталог, а не його вміст
# очікуваний результат drwx-wx-wt
```

Перевірка під іншим користувачем:

```
sudo -u <USER> touch <DIR>/secret.txt
# виконує команду від імені іншого користувача
# дозволено, бо є право на запис і прохід

sudo -u <USER> ls -l <DIR>
# Permission denied, бо немає права читати список файлів
```

Власник каталогу бачить і читає файл як завжди. Якщо потрібна конфіденційність самого вмісту файлу, а не лише його існування, додатково потрібні жорсткі права на сам файл, наприклад 600. Сам «темний» каталог ховає лише перелік імен, а не вміст конкретного файлу, якщо хтось знає його точну назву.
